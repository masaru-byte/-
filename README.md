# けあしる

### 介護の「見えない時間」を可視化し、保険外サービスを探す

> 介護サービスを検索するプロダクトではなく、**家族が失っている時間を可視化し、それを買い戻す方法を提示する**プロダクト。

---

## 解決したい課題

介護保険の給付対象にならない「保険外サービス」（必要性が比較的低い外出の付き添い、部屋の掃除など、実費で払うサービス）には、次の構造的な問題があります。

| 立場 | 課題 |
|---|---|
| **家族・親族** | どんな保険外サービスが受けられるのか分からない。自分が週に何時間介護に使っているかも自覚できていない |
| **ケアマネジャー** | 保険外サービスをケアプランに入れても加算が発生せず、紹介責任だけを負うため、案内するインセンティブがない |
| **自治体** | 総合事業・生活支援体制整備事業において、どの地域・時間帯に未充足の需要があるか把握できていない |

保険外サービスを利用したいという人は6割近く存在し、そのうち3割ほどは「知っていれば活用したかった」と答えています。家族が介護の情報を得る主な手段はケアマネジャーですが、上記の理由で情報が届きません。

**必要なのは、市民が自発的に探せる状態をつくることと、ケアマネジャー・地域包括支援センター側からアプローチできる材料を用意することです。**

## 画面構成

### 1. ケアタイムライン（市民向け・中心画面）

5ステップの入力（要介護認定の区分 → 世帯状況 → 困っていること → 発生する曜日・時間帯 → 月の予算）を終えると、**7日 × 4時間帯 = 28マスの週間タイムライン**が、すでにサービスを当てはめた状態で表示されます。

- マスの色分け … 家族が担う（赤）／ 保険給付・総合事業（緑）／ 保険外・自費・互助（橙）／ 予定なし（灰）
- 予算スライダーを動かすと、その金額に収まる組み合わせを即座に組み直します（0〜20万円）
- マス目をクリックすると候補サービスの一覧が出て、出典URL・原文抜粋・確認日つきで差し替えられます
- 「このプランで使うサービス」一覧で、種類・週の回数・月額を一覧できます
- A4 1枚に印刷して、ケアマネジャーや家族との相談に持ち込めます

困りごとの入力は**タスクごとに曜日と時間帯を選ぶ方式**です（例：「朝夕の調理」→ 毎日 × 朝・夕方）。

### 2. 自治体ダッシュボード

- **サービス種別ごと**の「曜日 × 時間帯 × 対応できる事業所数」ヒートマップ（供給側は登録データから実際に集計）
- 未充足需要ランキング、町丁目別のサービス空白度

### 3. サービス管理

収集したサービス情報の一覧・検索・承認ステータス管理コンソール。

## 中核ロジック

### 予算制約つき 効率順の割り当て

```
効率 = 削減できる家族時間 ÷ 1回あたりの自己負担額
```

効率の高い順に、月額予算の範囲でサービスを割り当てます。介護保険給付は要介護区分ごとの区分支給限度基準額（単位数上限）を参照し、超過分は10割負担として計算します。予算0円の場合は、無償のボランティア・互助・自治体施策のみで構成します。

### 出典の保持

料金・対象条件は原文抜粋（`priceSourceSnippet`）と出典URLを保持し、UI上でも確認できます。

## 技術スタック

- **フロントエンド**: Next.js 16 (App Router) + TypeScript + Tailwind CSS v4
- **アイコン**: Lucide React
- **データ収集**: Python 3（`crawler/collect_services.py`）

## 現状の制約（プロトタイプ）

公開にあたって、実装が追いついていない点を明記します。

- **サービスデータ**: 手作業で作成した30件をもとに、地域名を変えた派生レコードを機械生成して170件にしています。生成分の料金根拠はプレースホルダであり、実在の事業者情報として扱えません
- **クローラ**: `crawler/collect_services.py` は処理の流れを示すスケルトンで、実際のHTTP取得とLLM抽出は未実装です
- **自治体ダッシュボード**: 供給側（対応事業所数）は登録データから実際に集計していますが、検索ログ・需要側の数値と町丁目データはシミュレーション値です
- **共有リンク**: URLを発行するのみで、状態の保存・復元は未実装です
- **API Routes**: `src/app/api/` 配下は実装済みですが、現在の画面はすべてクライアント側で計算しており、これらを呼び出していません
- 要介護度・世帯状況によるサービス適合判定に未実装の分岐が残っています
